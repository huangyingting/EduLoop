# Authentication

EduLoop uses Auth.js (`next-auth` v5) for email/password, Google, Microsoft Entra ID, and Facebook sign-in. Guests can practice immediately without receiving an identity or durable record. Registering or signing in starts or resumes the authenticated account's learner profile.

## Auth.js flow

- `src/auth.ts` is the single Auth.js configuration. It owns providers, the Prisma adapter, credential verification, callbacks, session projection, and OAuth sign-in events.
- `GET|POST /api/auth/[...nextauth]` exposes Auth.js' CSRF, provider, callback, session, sign-in, and sign-out endpoints.
- `POST /api/auth/register` remains an EduLoop endpoint because Auth.js Credentials authenticates existing users but deliberately does not create password users. In production it creates an unverified account and schedules email delivery after returning; Credentials refuses the correct password until verification succeeds. The link recipient must re-enter the registration password, preventing an unsolicited link from activating a password chosen by somebody else. Development without a configured email provider auto-verifies new accounts so the local setup remains self-contained.
- Credentials authentication claims the exact password-hash and `sessionVersion` snapshot that it verified. A login-time bcrypt cost upgrade uses that guarded claim instead of writing by user ID, and the resulting JWT carries the claimed version rather than adopting whatever version exists later in the callback. Password rotation or all-device revocation therefore defeats an already in-flight old-password login; two valid logins racing the same legacy-hash upgrade may retry only while the original security version remains unchanged.
- `POST|PATCH /api/auth/email-verification` resends and consumes 24-hour, single-use email verification links. Resend responses are generic, social-only accounts without a password do not receive ordinary verification links, account lookup and delivery happen after the response, URL fragments keep tokens out of requests and referrers, and only SHA-256 token digests are stored. Issuance leaves the last provider-accepted link valid while a replacement is in flight; a failed send removes only that new proof, while acceptance atomically retains the newest issued-and-delivered proof even when provider responses finish out of order. Completion requires the current password, claims the token and password/session snapshot atomically, revokes every session and pending account proof, and removes provider associations when this is the account's first trustworthy mailbox proof.
- Google, Microsoft, and Facebook use Auth.js providers. Buttons appear only when that provider has a complete client-ID/client-secret pair. Only Google's literal `email_verified: true` claim can establish mailbox assurance, and only when the normalized claim exactly matches the current EduLoop login address. A matching Google address still cannot auto-link an existing account: the learner must first authenticate through a remaining method and explicitly connect Google from `/privacy`. Microsoft and Facebook addresses remain unverified until an EduLoop email-verification, password-reset, or email-change link proves control of that mailbox.
- OAuth navigation requests a fresh Auth.js CSRF proof and authorization URL without reflecting provider response bodies. Provider-discovery or initiation failures leave email/password controls usable, show a fixed retry message, and clear the busy state. Callback rejection, outage, configuration, account-conflict, and stale-request codes map to bounded messages; an authenticated account-link failure stays on a dedicated recovery view with an explicit route back to `/privacy` instead of being redirected through a loop. A successful account sign-in ensures that the user owns one learner profile; guests have no profile or progress to merge.
- `PATCH|DELETE /api/auth/account` provides password setup/rotation and full account erasure. Password changes use optimistic password-hash and authenticated-session-version guards before revoking every session and outstanding account-proof token. Setting the first password never proves mailbox ownership: an unverified social account receives a fresh verification link and remains unable to use Credentials. The recipient must re-enter that password; successful proof removes the previously untrusted provider connection, after which the user signs in with the password and may explicitly reconnect the provider. Verified password changes send a security notice when email delivery is configured. Deletion binds the confirmed password and cascading user-row delete to the exact version authenticated by the request, refuses a concurrent revocation or security change, and sends a final notice; social-only deletion is confirmed with the account email.
- `DELETE /api/auth/provider` removes a linked Google, Microsoft, or Facebook identity after a login no older than 10 minutes. It binds the transition to that session's exact database version, refuses to remove the final login method, deletes the stored provider association and pending account-proof tokens, revokes every session, and sends an account-security notice when email delivery is configured.
- `DELETE /api/auth/sessions` lets a user explicitly sign every device out after a login no older than 10 minutes, including from a provisional account that has not accepted the current legal versions. An optimistic `sessionVersion` guard permits exactly one concurrent rotation; adapter sessions and every pending account-proof token are deleted in the same transaction, and a security notice is sent when email delivery is configured.
- `POST|PATCH /api/auth/email-change` requires the current password or a social login no older than 10 minutes, sends a 60-minute single-use confirmation link to the new address, and changes the login identity only after that address is verified. Issuance atomically claims the exact authenticated `sessionVersion`, so a request delayed behind password recovery, session revocation, or another security mutation cannot recreate a proof after that mutation clears old tokens. A delivery failure removes only the attempted replacement; provider acceptance selects the newest issued-and-delivered change while retaining in-flight requests until their outcome is known. Completion claims the user security snapshot before the proof token, matching verification and recovery lock order; it revokes every prior session and sends a security notice to the previous address. Address uniqueness is checked both when the link is issued and atomically when it is consumed.
- `POST|PATCH /api/auth/password-reset` issues and consumes 30-minute, single-use password reset links. Requests return a generic response before account lookup and email delivery run as a post-response task, and only a SHA-256 digest is stored. As with verification and email change, an accepted link is not invalidated until a newer issued proof is accepted; failed and out-of-order replacement deliveries cannot strand the learner without the newest successfully delivered link. Every post-response operation is registered under a closed task name and has a final privacy-safe structured failure guard in addition to its delivery-specific handling. A successful reset uses password/session snapshot guards, verifies email ownership, revokes every session and outstanding account-proof token, and sends a security notice. If the account was not already email-verified, the same atomic transaction removes every provider association so the original untrusted social identity and the mailbox owner cannot share the account; providers on an already verified account are preserved.
- Expired adapter sessions, Auth.js verification records, hashed email-verification, email-change, and password-reset proofs, and keyed rate-limit pseudonym buckets are deleted together. Normal traffic triggers an indexed cleanup every 250 limiter operations, while `npm run data:cleanup` gives low-traffic deployments a deterministic scheduled path.
- New production password registrations carry an explicit 30-day expiry until mailbox verification. Verification and recovery links are capped at that fixed deadline, so resends cannot extend an abandoned registration indefinitely. Cleanup deletes only an expired `LEARNER` password registration with no provider, live session or proof, operator history, or learning/report activity; empty profile preferences and the registration consent record cascade with the account. A registration request can reclaim that released email in the same request. The paired migration gives eligible legacy registrations a fresh 30-day deployment grace instead of deleting them immediately.
- OAuth/OIDC linking persists only the provider type and stable account identifier required for later sign-in. Access, refresh, and ID tokens, provider session state, scopes, token type, and expiry metadata are discarded before the Prisma adapter writes; the paired migration nulls credentials retained by earlier releases.
- `POST /api/auth/consent` records the current terms/privacy versions plus an `ADULT` or `GUARDIAN` basis in both the user snapshot and append-only `ConsentRecord`. Password registration records consent atomically. Existing and new OAuth accounts without current consent receive a provisional session, but persistent APIs reject it and no learner profile is created until acceptance. `/privacy` remains accessible; complete export and learning-data deletion remain available after recent reauthentication, and full account deletion remains available after account confirmation, so legal rights do not depend on accepting new terms. Learning-data erasure locks the exact authenticated session version before deleting the learner graph, so an in-flight stale request loses to account-wide revocation. Export format v3 includes account identity and registration-retention metadata, linked-provider identifiers, consent history, safe pending-action and session-expiry metadata, applicable content-review actions, and every semantic learner field, including streak shields and review/report lifecycle timestamps, while excluding database linkage and idempotency keys, password hashes, session tokens, and token digests.

One `User` owns exactly one `LearnerProfile` once the account is used. Authenticated learner APIs resolve the user from the Auth.js token and never accept a client-supplied learner identity. Attempts, practice sessions, reports, badges, daily activity, saved questions, and review items are available only to signed-in users.

Guests may open `/practice`, fetch public catalog/questions/hints, and submit an answer for immediate grading. That branch creates no learner, attempt, session, activity, review item, report, XP, or badge; written-response self-assessment and ten-question counters remain only in page memory. All other pages redirect to `/login`, and persistent APIs independently return `401` without a valid Auth.js session.

## Sessions and revocation

Credentials requires Auth.js' JWT session strategy. Auth.js encrypts the JWT as an HttpOnly, SameSite=Lax cookie and marks it Secure in production. `AUTH_SECRET` encrypts sessions and keys domain-separated rate-limit pseudonyms; it must contain at least 32 random characters in production.

Every token contains the user's `sessionVersion`. Server authorization reads the current user from Prisma and accepts the token only when its version still matches. A Credentials token is initialized from the exact hash/version snapshot claimed after password verification, not from a later account read, so a concurrent password reset or revocation cannot turn a stale proof into a current session. Explicit all-device sign-out, password setup or rotation, first mailbox verification, verified login-email changes, and provider disconnection increment the version, invalidating every prior browser token before the client signs in again. Adapter `Session` rows are also removed. Deleting the user invalidates all tokens immediately. Roles, linked providers, display name, email-assurance state, and password availability are refreshed from the database rather than trusted as stale token claims.

The JWT also carries an explicit `authenticatedAt` timestamp set only when Auth.js completes a credential or provider sign-in. It is preserved when Auth.js rotates the JWT instead of relying on the token's refreshable `iat`. Complete account export, irreversible learning-data deletion, all-device sign-out, linking or removing a provider, social-only email change, password setup or account deletion, and every privileged content-studio read or mutation require this authentication to be no more than 10 minutes old. Every one of those high-impact mutations additionally claims the exact `sessionVersion` returned by authentication inside its database transaction; content transitions also claim the operator role. A request already in flight can finish only if it orders before revocation or demotion, never by silently adopting the newer security state. The studio guard covers full answer context, aggregate learning metrics, quarantine, resolution, and reopening at the API layer; the browser removes that workspace when the same deadline passes and offers a deliberate sign-out-and-reauthenticate path. Older and pre-migration tokens must sign in again; password-backed changes continue to require the current password. Password setup, rotation, or recovery also deletes adapter sessions and every pending verification, email-change, and password-reset token so an older proof cannot survive newly secured credentials.

The Auth.js migration retains existing `User` rows and bcrypt hashes but drops legacy `AuthSession` rows. The later email-assurance migration preserves every user, password hash, provider association, and learner record, but prior verification timestamps lack trustworthy proof provenance. It therefore clears those timestamps, increments the affected users' session versions, and removes their adapter sessions. Applying it signs those browsers out once: password users must consume a new email link, matching verified Google users regain assurance on their next Google sign-in, and Microsoft/Facebook users can continue social sign-in while proving ownership. The mailbox-ownership migration then deletes only legacy ordinary verification links for accounts without a password because those links cannot satisfy the new password-binding requirement; password-reset recovery remains available. Auth.js adapter models are `Account`, `Session`, and `VerificationToken`; `Session` is present for adapter compatibility but the current Credentials-compatible configuration uses encrypted JWT sessions.

## Account linking policy

- A provider identity already stored in `Account` signs into its owning user without a retained provider bearer credential. The sign-in callback records that identity's user and `sessionVersion`; cookie issuance rechecks the exact provider connection and version, so a callback already in flight cannot survive disconnection by silently adopting the newer security state.
- A signed-in user can connect any unclaimed configured provider from `/privacy` after reauthenticating within 10 minutes. Auth.js verifies the session before linking, and the adapter persists the provider only while that exact database `sessionVersion` remains current; a concurrent mailbox recovery therefore removes the link or makes the stale callback fail.
- A recently authenticated user can remove a provider from `/privacy` only when another provider or a password backed by a verified email remains. An unverified password is deliberately not counted as a usable fallback login method. The mutation uses an optimistic `sessionVersion` claim so simultaneous removals cannot delete every login method, removes the credential-free provider identity record, and signs every browser out.
- Google never auto-links an existing same-email user. Its literal verified-email claim can establish assurance for a new Google account or an explicitly connected identity, but the user must authenticate the existing EduLoop account before linking.
- Microsoft email claims are not used for automatic linking, including with a tenant-pinned issuer. Sign in with the existing account first and connect Microsoft from `/privacy`.
- Facebook does not expose an equivalent verified-email claim, so same-email auto-linking remains disabled. Facebook accounts without an email are rejected.
- A verified provider claim never blesses a different current EduLoop address. This matters after a verified email change or when a signed-in user links a provider whose mailbox differs from the account mailbox.

## Environment

Use these callback URLs in provider consoles:

- `{AUTH_URL}/api/auth/callback/google`
- `{AUTH_URL}/api/auth/callback/microsoft-entra-id`
- `{AUTH_URL}/api/auth/callback/facebook`

Register only the callback for the intended production origin, keep development and preview credentials in separate provider applications, and do not use wildcard callbacks. Confirm the provider application's publication mode, allowed tenant or audience, requested profile/email permissions, support and privacy metadata, and dedicated test identities in the provider console. `npm run smoke:oauth` safely confirms deployed discovery, CSRF issuance, authorization initiation, exact authorization host, required request parameters, and the exact callback URI without following the provider URL or logging sensitive values. It does not validate the client secret, consent screen, callback exchange, claims, linking, persistence, or disconnection; every enabled provider still requires the interactive launch journey in `docs/operations.md`.

Production requires a generated `AUTH_SECRET`, a public HTTPS `AUTH_URL`, `RESEND_API_KEY`, a verified `AUTH_EMAIL_FROM` sender, and the legal entity/contact/jurisdiction values rendered by `/terms` and `/privacy-policy`. Generate the secret with `npx auth secret`, then transfer it through a protected workflow into the deployment secret manager and remove any temporary local copy; startup and runtime reject common placeholders, whitespace, low-diversity values, and values outside the bounded generated-secret size. Provider variables are documented in `.env.example`; incomplete email, legal, or social-provider configuration fails `npm run env:check`. `npm run smoke:email` sends one explicitly confirmed, link-free message through the production account-email transport and emits only a random probe ID; HTTP acceptance must be followed by a matching provider delivered event, inbox receipt, SPF/DKIM/DMARC inspection, and deployed verification/recovery journey. Login, registration, email verification, password recovery, and email-change proof completion enforce both a trusted-address ceiling and a separate normalized-email or proof-token ceiling, so address rotation cannot bypass the target limit and identifier rotation cannot bypass the source limit. Authenticated consent and account actions are bounded by account across address changes. Every bucket ID is a window-scoped HMAC-SHA-256 pseudonym keyed by `AUTH_SECRET` and shared by all application replicas; raw network addresses, emails, account IDs, and proof tokens are never persisted in limiter rows. Rotating `AUTH_SECRET` starts a fresh limiter namespace, so keep ingress-level abuse protection active through the rotation while older rows expire normally.

Auth.js error logging is overridden with structured `authjs_error` records containing only a bounded error class and safe Auth.js type. Provider messages, callback query values, causes, URLs, authorization codes, and tokens are excluded. Browser recovery tests exercise provider discovery failure, provider-start failure, and a real rejected callback without contacting an external provider.

Custom state-changing endpoints compare the browser `Origin` with `AUTH_URL` in production. Forwarded host headers are only a local-development fallback and cannot redefine the accepted public origin. The container assumes one trusted reverse proxy when selecting a client from `X-Forwarded-For`; set `TRUSTED_PROXY_HOPS` to the exact trusted chain depth when a CDN or another proxy is added.

MFA, guardian consent, approved institutional identity, and institutional account lifecycle remain separate requirements for school-managed deployment.
